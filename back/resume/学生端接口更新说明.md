# 学生端接口更新说明

## 🔄 更新内容

### 核心逻辑变更

原逻辑：直接通过userId查询student表  
新逻辑：userId → user表 → username(学号) → student表

### 详细流程

```
1. 从Token中获取userId
   ↓
2. 根据userId查询user表获取用户信息
   ↓
3. 获取user.username（即学号）
   ↓
4. 根据学号(stuId)查询student表
   ↓
5. 执行完善信息或上传简历操作
```

## 🔑 关键假设

### username即学号

系统假设：**user表的username字段存储的是学生的学号**

示例：
```sql
-- user表
user_id | username | user_type
   1    | 20230001 | student

-- student表  
id | stu_id   | name
1  | 20230001 | 张三
```

关联关系：`user.username = student.stu_id`

## ✅ 优势

1. **数据一致性**：确保操作的学生与登录用户对应
2. **安全性提升**：通过user表验证用户存在性
3. **符合业务逻辑**：学号作为唯一标识贯穿user和student表
4. **便于扩展**：如果user表与student表关系变化，只需修改查询逻辑

## ⚠️ 注意事项

### 1. username必须是数字

代码中使用 `Integer.parseInt(user.getUsername())`，因此：
- ✅ 正确：username = "20230001"
- ❌ 错误：username = "student001"

如果username包含非数字字符，会抛出`NumberFormatException`。

### 2. 数据一致性

确保每个student记录都有对应的user记录：
```sql
-- 检查不一致的数据
SELECT s.stu_id, s.name 
FROM student s 
LEFT JOIN user u ON s.stu_id = CAST(u.username AS UNSIGNED)
WHERE u.user_id IS NULL;
```

### 3. user_id与stu_id的区别

- `user.user_id`: user表的主键，自增
- `student.stu_id`: 学号，业务唯一标识
- `student.id`: student表的主键，自增

关系：`user.username = student.stu_id`

## 🔍 错误排查

### 问题1：提示"用户不存在"

**原因：** Token中的userId无效或user表中没有该记录

**排查：**
```sql
-- 检查token中的userId
SELECT * FROM user WHERE user_id = {userId};
```

### 问题2：提示"学生信息不存在"

**原因：** user.username在student表中找不到匹配的stu_id

**排查：**
```sql
-- 检查user.username与student.stu_id是否匹配
SELECT u.username, s.stu_id, s.name
FROM user u
LEFT JOIN student s ON u.username = CAST(s.stu_id AS CHAR)
WHERE u.user_id = {userId};
```

### 问题3：NumberFormatException

**原因：** user.username不是纯数字

**解决：** 确保username字段存储的是学号数字，如"20230001"
